# 03. Сети: почему curl работает на сервере, но не с другого узла

**Время:** 4–6 часов. **Перед началом:** лаба 02, доступ к обеим VM.

## Цель

Различать DNS, маршрутизацию, TCP, прослушивание порта, firewall и HTTP.
Диагностировать запрос последовательно, от клиента к приложению.

## Задания

1. На обеих VM запиши интерфейсы, адреса/маски, default route и используемый resolver.
   Покажи маршрут до второй VM через `ip route get`. Объясни, какие адреса приватные,
   где NAT провайдера и какой адрес сервер видит у входящего клиента.
2. Пока API слушает `127.0.0.1:8080`, проверь его с `app` и с `mon`. Через `ss`
   докажи причину различия. В варианте с приватной сетью переключи `APP_HOST` на
   реальный private IP и разреши этот порт только для `mon`. В варианте с туннелями
   оставь loopback и сделай проброс `mon:18080 → app:8080`.
3. Собери таблицу «источник → адрес назначения → порт → результат». Проверь localhost,
   приватный адрес и разрешённый внешний доступ. Не сканируй чужие сети.
4. Сравни `dig`, `getent hosts`, `/etc/hosts` и ответ приложения по имени.
   Используй имя `ops-demo.test` в `/etc/hosts` для своего стенда; домен `.test`
   не требует регистрации. Объясни, почему `dig` не читает `/etc/hosts`.
5. Запиши через `tcpdump` только обмен с учебным HTTP-портом: SYN, SYN-ACK, ACK,
   HTTP-запрос, ответ и закрытие. Ограничь capture по числу пакетов и размеру файла.
   Сопоставь TCP-пакеты с `curl -v`. В отчёт положи обезличенную расшифровку.
6. Через `curl -w` сравни DNS/connect/time-to-first-byte/total для `/healthz` и
   `/slow?ms=700`. Объясни, на каком этапе выросло время.
7. Создай SSH-туннель к UI будущего мониторинга, проверь `ExitOnForwardFailure`
   и разрыв при завершении SSH. Используй `ServerAliveInterval` для обнаружения
   потерянного соединения. Для межсерверного туннеля нужен отдельный ограниченный
   SSH-ключ, а не копия твоего основного приватного ключа.
8. Открой `https://example.com` и разложи запрос на DNS → TCP → TLS → HTTP.
   Посмотри сертификат через `openssl s_client` с SNI. Изучи на своём соединении,
   чем HTTPS отличается от открытого HTTP в packet capture.

## Инциденты

| Сбой | Безопасное воспроизведение | Проверка перед исправлением |
|---|---|---|
| Connection refused | Обратиться на незанятый порт своей VM | Есть ли listener; какой TCP-ответ пришёл |
| Timeout | Временно DROP только учебного порта от второй VM | Доходит ли SYN; какое правило и какой firewall его отбрасывает |
| Ошибка имени | Опечатка в имени `.test` или записи `/etc/hosts` | Resolver, `getent`, `dig`, затем запрос по IP |
| Адрес отвечает, сервис другой | Указать в curl неверный порт существующего учебного сервиса | HTTP-код, заголовки и процесс-владелец listener |
| Туннель исчез | Завершить только процесс учебного SSH-туннеля | Локальный listener, SSH-журнал, прямая доступность endpoint на сервере |

Для DROP заранее сохрани правила и подготовь точную команду удаления **этого одного
правила**. Не меняй политику всего firewall, порт SSH или default route. Если
провайдер фильтрует раньше гостевой ОС, отсутствие SYN в capture — полезное наблюдение,
а не доказательство падения приложения. Вариант с туннелем проверяй по проброшенному
порту; не закрывай SSH, имитируя HTTP timeout.

## Приёмка и что сдать

- Схема прохождения пакета и таблица разрешённых соединений, включая IPv6.
- API доступен от `mon` выбранным способом и закрыт от посторонних адресов.
- Для каждого инцидента есть наблюдение, определяющее слой проблемы, и проверка после исправления.
- Понимаешь разницу «имя не разрешилось», «TCP не установился», «HTTP 500».
- Туннель к Grafana готов; рабочие правила firewall восстановлены.

## Контрольные вопросы

1. Почему успешный `ping` не доказывает доступность API, а неуспешный не доказывает обратное?
2. Чем отличаются bind на `127.0.0.1`, конкретный private IP и `0.0.0.0`?
3. Где действуют security group провайдера и firewall внутри VM?
4. Что меняет `curl --resolve`, и проверяет ли он реальную работу DNS?
5. Когда нужен UDP, а когда TCP? Как DNS может использовать оба протокола?

Подсказки: `ip -br a`, `ip route`, `ss -lntup`, `resolvectl status`, `dig`,
`getent`, `nc -vz`, `curl --connect-timeout 2 --max-time 5`, `tcpdump -nn`.

Документация: [Ubuntu networking](https://ubuntu.com/server/docs/how-to/networking/).
Синтаксис инструментов проверяй через `man ip`, `man ss`, `man tcpdump`, `man ssh`.

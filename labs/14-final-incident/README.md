# 14. Итоговая работа: восстановить сервис по наблюдаемым признакам

**Время:** 5–8 часов. **Перед началом:** минимум лабы 02–11. Terraform и Kubernetes
можно сдать отдельными расширениями после этой работы.

## Сценарий

Ты отвечаешь за учебный API. Пользователь жалуется на ошибки после релиза, часть
проверок зелёная. Нужно определить причину, восстановить доступность, доказать
сохранность данных и написать инструкцию для следующего дежурного.

Используй Compose-стенд, чтобы Prometheus/Grafana/Loki работали одновременно.
Если выполнял kind на `mon`, предварительно верни мониторинг в штатное состояние.

## До инцидента

1. Доведи bootstrap, pipeline, backup и rollback до состояния «повторяется по README».
2. Запиши SLI: доля успешных бизнес-запросов, исключая `/healthz`, `/readyz`, `/metrics`.
   Заранее определи, считаются ли 4xx успехом, и не меняй определение после сбоя.
3. Для учебного окна 30 минут задай SLO 99% успешных запросов. Посчитай допустимое
   число неуспешных запросов из **фактического** количества запросов. Это учебный
   request-based SLO, его бюджет не равен автоматически 18 секундам простоя.
4. Подготовь ограниченную нагрузку с постоянным темпом, например 1 req/s, не дольше
   30 минут. Сохрани результаты клиента независимо от метрик сервера: если сервер
   недоступен, его собственный counter не учитывает все неудачные попытки клиента.
5. Сохрани рабочий digest, env/config, backup и значения `/items`.

## Введение неисправностей

Выполни 3 случая по одному: обязательно повреждение данных с восстановлением из
backup и неудачный релиз с rollback; третий выбери из таблицы. Для проверки навыка
можно попросить друга выбрать детали случая, не сообщая причину; самостоятельное
выполнение тоже подходит.
Перед каждой неисправностью запиши точный способ возврата рабочего состояния.

| Класс | Неисправность только в учебном проекте |
|---|---|
| Конфиг | Релиз с неверным DATA_DIR, процесс жив, readyz=503 |
| Данные | Некорректный JSON в учебной копии items.json |
| Сеть | Остановленный SSH-туннель scrape при живом API |
| Proxy | Неверный upstream-port или read timeout меньше задержки `/slow` |
| Доставка | Образ доступен, но env релиза невалиден, нужен откат конфига |
| Наблюдаемость | Остановленный Alloy при работающем приложении |

Не отключай SSH, не заполняй корневой диск и не меняй глобальный firewall.
После каждого случая полностью восстанови baseline перед следующим.

## Во время инцидента

1. Зафиксируй первый пользовательский симптом, время обнаружения и firing алерта.
2. Сначала локализуй слой: DNS/сеть → proxy → процесс → readiness/данные → ресурсы.
   Проверь, не сломался ли только сам мониторинг.
3. Сохрани короткие доказательства до исправления: ID запроса, лог, метрику,
   состояние порта или diff конфигурации. Проверяй гипотезу одной командой за раз.
4. Восстанови релиз либо данные проверенным способом. Не удаляй неисправную копию
   до сохранения доказательств. Запиши время восстановления и потерянные изменения.
5. Подтверди восстановление клиентской проверкой, `/readyz`, `/items`, метриками
   и resolved. Наблюдай ещё 5 минут; алерт может очищаться с задержкой окна/`for`.

## Результат

Сдай в одной папке:

- README: схема, версии, bootstrap, deploy, rollback, backup/restore и очистка ресурсов.
- Runbook «API недоступен» с командами и ожидаемыми ответами для каждого слоя.
- Timeline UTC: начало сбоя, обнаружение, локализация, исправление, подтверждение.
- Клиентский SLI за 30 минут, расход error budget и сравнение с серверными метриками.
- Postmortem каждого случая: влияние, первопричина, что помогло/мешало, два конкретных
  улучшения с проверяемым результатом. Формулировка «быть внимательнее» не подходит.

## Приёмка

- Три неисправности воспроизведены, локализованы по доказательствам и устранены.
- Одно восстановление выполнено из внешней копии backup, одно — через rollback релиза.
- Знаешь ограничения: одна VM не даёт HA, две VM в одном аккаунте не дают независимый
  disaster recovery, пустой график не означает отсутствие ошибок.
- Другой человек может повторить запуск и диагностику по твоему README, не спрашивая
  значения путей и скрытые ручные действия. Если проверял только сам — так и укажи.

## Что изучать дальше

После этого маршрута выбери направление по пробелам, найденным в инцидентах:
PostgreSQL и миграции/восстановление; полноценные tracing и OpenTelemetry;
облачные IAM/VPC/load balancers; Kubernetes networking/storage/RBAC;
управление секретами; GitOps и Helm. Для каждой темы добавляй один проверяемый
сценарий сбоя и восстановления, а не только установку нового инструмента.

# 04. Диагностика ресурсов: медленно — это ещё не причина

**Время:** 3–4 часа. **Перед началом:** лабы 02–03.

## Цель

Сопоставить симптом HTTP с состоянием CPU, памяти, файловой системы и конкретного
процесса. Научиться собирать данные до перезапуска сервиса.

## Задания

1. Сними минутный baseline: `uptime`, `free`, `vmstat`, `iostat`, `pidstat`, `df`
   по байтам и inode. Первый отчёт некоторых утилит — среднее с загрузки;
   используй последующие интервальные выборки, например 1 секунду × 10.
2. Найди main PID API, его RSS, CPU, открытые файлы, лимит дескрипторов и сокеты.
   Сопоставь `systemctl show`, `ps`, `/proc/PID/limits`, `lsof`, `ss`.
3. Установи `stress-ng`. На учебной `app` запусти ограниченную нагрузку:

   ```bash
   stress-ng --cpu 1 --timeout 45s
   ```

   Во втором сеансе наблюдай CPU, run queue, load average, steal time и HTTP latency.
   Доля занятого CPU зависит от числа vCPU. Зафиксируй, если latency не изменилась:
   это допустимый результат, а не повод увеличивать нагрузку без ограничений.
4. После завершения CPU-теста проверь память под небольшой нагрузкой:

   ```bash
   stress-ng --vm 1 --vm-bytes 128M --vm-keep --timeout 30s
   ```

   Сравни free/available/cache, RSS процесса и swap activity. Не доводи VM до OOM.
   Найди способ искать OOM-события в kernel journal, даже если их сейчас нет.
5. Отдельно вызови `/slow?ms=1500` несколько раз без CPU-нагрузки. Докажи, что высокая
   latency возможна при свободном CPU. Сравни с наблюдениями предыдущего эксперимента.
6. Найди топ каталогов по размеру **только в учебных данных** и сравни `du` с `df`.
   Объясни сценарий удалённого, но открытого файла через `lsof +L1`.
7. Исследуй диск: размер, свободное место, inode, read/write latency и загрузку.
   Не создавай файлы до заполнения корневого диска; маленький изолированный
   файловый образ для ENOSPC будет дополнительным заданием в лабе 07.

## Мини-инциденты

- «Load average выше числа vCPU»: какие ещё данные нужны, чтобы обвинить CPU?
- «Память почти вся used»: доступна ли она приложению, начался ли swap/OOM?
- «HTTP медленный, ресурсы свободны»: что показывают endpoint, логи и задержки curl?
- «На диске место есть, файл не создаётся»: проверь inode, права и read-only mount.

Для последних случаев достаточно дерева диагностики; не нужно ломать корневую FS.

## Приёмка и что сдать

- Таблица baseline / CPU-test / memory-test / slow endpoint: CPU, load, available
  RAM, swap, HTTP latency; у каждой цифры есть единица и интервал измерения.
- Два графика или сохранённые интервальные выборки с объяснением поведения.
- Runbook «сервис медленный»: до 10 последовательных проверок с ветвлением
  по наблюдениям, включая DNS/сеть и состояние приложения.
- Нагрузка завершилась, посторонних stress-процессов нет, API отвечает.

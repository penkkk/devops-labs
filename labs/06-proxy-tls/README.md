# 06. Nginx, HTTP и TLS

**Время:** 3–5 часов. **Перед началом:** лабы 02–05.

## Цель

Поставить reverse proxy перед API, настроить проверяемый HTTPS и отличать ошибку
proxy от ошибки приложения. Домен и платный сертификат не нужны.

## Задания

1. На `app` установи Nginx и настрой `ops-demo.test` → `127.0.0.1:8080`.
   Верни API на loopback. Если Prometheus раньше ходил на private IP:8080,
   переведи scrape на SSH-туннель либо отдельный закрытый location `/metrics` Nginx
   с allow только для `mon`. Публичный listener не должен открывать `/fail`, `/slow`
   и `/metrics` посторонним: ограничь весь учебный vhost своими адресами и `mon`.
2. Настрой отдельные access/error logs, передачу Host и `X-Request-ID`.
   Пусть Nginx создаёт `$request_id`, передаёт его API и пишет в access log вместе
   со status, upstream_status, request_time, upstream_response_time.
   Найди один запрос одновременно в access log и JSON-журнале приложения.
3. Добавь TLS с самостоятельно подписанным учебным сертификатом с SAN
   `DNS:ops-demo.test`. На клиенте проверяй его через `curl --cacert` и правильное
   имя: `/etc/hosts` или `--resolve`. Перенаправляй HTTP на HTTPS.
4. Открой HTTPS со своего компьютера. Если HTTP доступен только через SSH-туннель,
   пробрось TLS на локальный 18443 и используй соответствующий порт в curl.
   Проверь срок действия, SAN, SNI и HTTP-код. `-k` используй только как
   диагностическое сравнение, затем верни проверку доверия.
5. Настрой таймауты соединения/чтения upstream. Временно сделай read timeout 1s
   и вызови `/slow?ms=1500`. Зафиксируй response code, обе стороны логов и метрики.
6. Проверь `nginx -t`, reload без потери работоспособности и ротацию файловых логов.
   Найди штатный logrotate-конфиг пакета, объясни reopen файла после rotation.

## Инциденты

| Симптом | Воспроизведение | Что сравнить |
|---|---|---|
| 502 | Остановить upstream либо указать незанятый upstream-port | Nginx error log, `ss`, прямой curl к API |
| 504 | Read timeout 1s при `/slow?ms=1500` | Тайминги proxy, продолжение обработки запроса приложением |
| 500 от приложения | Вызвать `/fail` | `status` и `upstream_status`, request ID |
| TLS verification failed | Неправильное имя либо отсутствие доверия сертификату | SAN, цепочка доверия, запрос с корректным именем и `--cacert` |
| Reload отклонён | Опечатка в копии конфига, затем `nginx -t` | Почему сначала проверяют конфиг, а не выполняют restart |

## Приёмка и что сдать

- Конфиг Nginx, обезличенные логи одного сквозного запроса и команды TLS-проверки.
- HTTPS проверяется без `-k`, HTTP перенаправляется, API напрямую не открыт в интернет.
- Метрики продолжают собираться после изменения bind приложения.
- Для 500/502/504 указаны разные причины и доказательства; таймауты возвращены в норму.
- Приватный ключ сертификата в Git не попал; тестовый сертификат помечен как учебный.

2. Почему увеличение таймаута не всегда исправляет причину задержки?
3. Что проверяет SAN, что SNI, а что доверие CA?
4. Почему 500 в метриках приложения и 504 у клиента могут относиться к разным слоям?

# 02. Логи и systemd: сервис запущен, а запросы падают

**Время:** 3–5 часов. **Перед началом:** [стенд](../00-stand/README.md) и ручной запуск API.

## Цель

Самостоятельно запустить приложение как службу, найти причину сбоя по журналу
и отличить работоспособность процесса от готовности обслуживать пользователей.

## Задания

1. Создай системного пользователя `opsdemo` без интерактивного входа. Разнеси код,
   конфиг и данные по путям из [описания приложения](../_shared/ops-demo/README.md).
   Код принадлежит root и доступен сервису на чтение; данные читает `opsdemo`.
2. Напиши `ops-demo.service`: `User`, абсолютный `ExecStart`, `WorkingDirectory`,
   `EnvironmentFile`, `Restart=on-failure`, пауза между рестартами, stdout/stderr
   в journal. Конфиг `/etc/ops-demo/ops-demo.env`: порт, версия, каталог данных.
   Относительный путь и `~` в `ExecStart` не используй.
3. Проверь unit, включи автозапуск, запусти службу. Сопоставь main PID, UID, порт
   и ответы `/healthz`, `/readyz`, `/items`. Найди запись `started` в journal.
4. Получи журнал только службы, текущей загрузки, за последние 10 минут и в live-режиме.
   Выгрузи сообщения приложения как JSON Lines и отфильтруй их через `jq`.
   У journal есть свои поля; JSON приложения находится в поле `MESSAGE`.
5. Настрой постоянное хранение journal через drop-in с лимитом 100 МБ.
   Проверь фактический размер и наличие журнала предыдущей загрузки после одного
   контролируемого reboot. Перед reboot проверь новый SSH-вход и консоль провайдера.
6. Разбери [синтетический журнал](../_shared/logs/incident.jsonl): посчитай HTTP-запросы
   по статусам, найди первый 5xx, три самых медленных запроса и долю 5xx **среди
   `http_request`**. Сравни версии 1.0/2.0/2.1. Сформулируй причину как гипотезу
   и укажи, какой проверки на сервере не хватает для её подтверждения.

## Введи и расследуй неисправности

Вводи по одной, сначала сохраняя рабочий конфиг и права.

| Сбой | Как воспроизвести | Что доказать |
|---|---|---|
| Не запускается | `APP_PORT=oops`, затем restart | Ошибка конфигурации в журнале, exit code, число рестартов |
| Не читает данные | Убрать у `opsdemo` чтение **копии учебного** `items.json` | 503 при живом процессе; проверка доступа от имени сервисного пользователя |
| Потерял готовность | Создать `/var/lib/ops-demo/not-ready` | `/healthz`=200, `/readyz`=503, PID прежний |
| Процесс аварийно завершился | Завершить только main PID службы сигналом SIGKILL | Новый PID и восстановление благодаря `Restart`; чем это отличается от `systemctl stop` |

После исправления восстанови права/конфиг, при необходимости выполни `reset-failed`
и подтверди 200. Стартовый лимит systemd может остановить бесконечные рестарты.
Изменение unit требует `daemon-reload`; изменение env читается при следующем старте.

## Приёмка и что сдать

- Unit и env без секретов; HTTP-проверки после старта и reboot.
- Четыре расследования с точным временем, командой проверки, причиной и исправлением.
- Сохранённые команды анализа журнала и результаты расчётов по JSONL.
- Лимит и постоянное хранение journal подтверждены. Сервис работает без root.

## Контрольные вопросы

1. Почему `journalctl -p err` может пропустить строку приложения с `"level":"ERROR"`?
2. Когда нужен `daemon-reload`, а когда достаточно restart?
3. Почему `active (running)` не доказывает доступность `/items`?
4. Чем journald retention отличается от logrotate для файлов Nginx?

Подсказки: `systemd-analyze verify`, `systemctl show`, `journalctl -u`, `-b`,
`--since`, `-f`, `-o json`, `-o cat`, `jq`, `sudo -u opsdemo`, `namei -l`.
Строки `started` и системные сообщения не всегда имеют поля HTTP-запроса: фильтруй
тип события перед арифметикой.

Документация: [journalctl](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html),
[journald.conf](https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html).
Для доступных именно в Ubuntu опций также читай локальные `man`.

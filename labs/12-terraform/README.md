# 12. Terraform: plan, state и drift

**Время:** 3–5 часов. **Перед началом:** лабы 08 и 10.

## Цель

Понять жизненный цикл инфраструктурного ресурса и разницу между Terraform state,
фактическим состоянием и желаемой конфигурацией. Облачный провайдер для основной
части не нужен: работаем с отдельными Docker-ресурсами на `mon`.

## Задания

1. Установи Terraform CLI по официальной инструкции, запиши версию. Создай отдельный
   каталог `solutions/12-terraform/infra`, не смешивая его с Compose основного сервиса.
2. Объяви версии Terraform и Docker provider, выполни init. Создай отдельную сеть
   и один учебный контейнер Nginx. Всем управляемым объектам дай префикс
   `devops-lab-tf-`; порт публикуй только на `127.0.0.1:18081`.
   Эти объекты не должны пересекаться с приложением, мониторингом или кластером.
3. Вынеси имя, host-port и закреплённый image в variables, добавь validation порта
   и outputs с URL и ID. Сохрани `.terraform.lock.hcl` в Git, state и `.terraform/`
   исключи. Локальный state пока достаточно, но храни его с ограниченными правами.
4. Выполни fmt, validate и plan. Объясни каждый создаваемый объект, затем сохрани
   plan в файл и примени именно его. Plan тоже не коммить: он может содержать секреты.
   Проверь HTTP-ответ через curl или SSH-туннель.
5. Выполни второй plan: изменений нет. Измени параметр порта; объясни, обновляется
   ли объект на месте или пересоздаётся. Подтверди новый listener и исчезновение старого.
6. Смоделируй drift: вручную удали **только контейнер с префиксом этой лабы**.
   Изучи следующий plan, восстанови через apply. Не редактируй state вручную.
7. Посмотри state list/show. Объясни, почему `sensitive = true` скрывает вывод,
   но не гарантирует отсутствие значения в state. Никакие настоящие секреты
   для этой лабы не нужны.
8. Составь destroy plan, убедись, что там только объекты этой лабы, и удали их.
   Проверь отсутствие контейнера, сети и listener. Основной стенд продолжает работать.

## Инциденты

- Порт уже занят: apply возвращает ошибку; определи фактическое состояние и исправь
  переменную, не удаляя посторонний процесс.
- Ресурс удалён вручную: plan обнаруживает расхождение и восстанавливает его.
- Потерян state: опиши восстановление из backup/import, не пробуй «лечить» потерю
  массовым удалением. Практический `import` одного своего объекта — дополнительное задание.

## Облачное продолжение, по желанию

После основной части выбери provider своего облака и подготовь **plan** одной
учебной VM, приватной сети и правил доступа. Перед apply выпиши цену, регион, лимиты,
теги, правила IPv4/IPv6 и процедуру удаления VM, дисков и IP. Не импортируй текущие
VPS в Terraform, пока не разобрался с планом и жизненным циклом ресурсов.
Конфигурацию ОС после создания передай Ansible, а не длинному shell provisioner.
Для совместной работы со state изучи backend с locking и разграничением доступа.

## Приёмка и что сдать

- HCL, lockfile, обезличенные create/no-change/drift/destroy plans и HTTP-проверка.
- Объяснение, кто управляет каждым объектом: Terraform, Ansible или Compose.
- После destroy остался рабочий основной стенд; учебные ресурсы удалены.
- Ни state, ни plans, ни provider credentials не добавлены в Git.

## Контрольные вопросы

1. Зачем state, если уже есть конфигурация и API провайдера?
2. Чем plan отличается от гарантии, что apply точно пройдёт?
3. Что означает drift и чем import отличается от создания нового ресурса?
4. Почему два инструмента не должны одновременно управлять одним контейнером?

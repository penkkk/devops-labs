# 11. Git и CI/CD: от commit до проверенного релиза

**Время:** 5–8 часов. **Перед началом:** Docker из лабы 08, автоматизация из лабы 10.

## Цель

Получить pipeline, который проверяет изменение, собирает неизменяемый артефакт
и доставляет его с проверкой готовности и понятным откатом.

## Подготовка

Используй собственный Git-репозиторий и доступный тебе CI. Пример платформы —
GitHub Actions; при GitLab CI этапы и критерии те же. Если удалённого репозитория
ещё нет, сначала выполни этапы локально, затем перенеси их в выбранный CI.
Проверь лимиты runner/registry в своём тарифе перед запуском.

Нужные навыки Git: ветка → commit → pull request → merge, просмотр diff и откат.
Выполни маленькое изменение `APP_VERSION` через этот цикл, если раньше не делал.
Секреты не должны попадать ни в коммиты, ни в артефакты, ни в logs.

## Задания

1. В PR запускай тесты учебного API:

   ```bash
   python3 -m unittest discover -s labs/_shared/ops-demo -p 'test_*.py' -v
   ```

   Тесты создают временный HTTP-server только на loopback. Добавь проверку Bash,
   Ansible syntax-check и Compose config для своих конфигов. Секреты для PR-проверок
   не нужны: используй явно фиктивные значения с той же структурой.
2. После merge собери образ **один раз**, обозначь commit SHA и получи digest.
   Запусти образ, дождись readiness, проверь `/items` и заверши тестовый контейнер.
   Неправильный ответ/timeout должен завершать job ошибкой.
3. Опубликуй прошедший проверки образ в свой registry. Раздели права проверки,
   публикации и deploy; задай минимальные permissions CI-токена. Сторонние actions
   закрепляй проверенным commit SHA. Не выполняй недоверенный PR-код с deploy-секретами.
4. Сделай ручной deploy job в собственное учебное окружение. Ручной запуск здесь —
   учебный способ управлять релизом, не обход проверки. Сериализуй deploy, чтобы
   два pipeline не перезаписывали друг друга. Передай в Ansible точный digest,
   а не изменяемый тег `latest`.
5. Выбери путь доступа CI к VPS: существующий VPN/SSH endpoint с ограничением
   источников, либо изолированный self-hosted runner на `mon`. Для последнего
   разрешай только доверенные задания своего репозитория. Не открывай SSH всему
   интернету ради непостоянных адресов hosted runners.
6. После deploy проверяй `/readyz`, `/items`, TLS и ожидаемую версию через `/`.
   Health gate имеет timeout. Храни предыдущий digest; при неготовности верни его
   и проверь восстановление. Напиши, какие изменения данных rollback образа не отменяет.
7. Сохрани release manifest: commit, digest, версии инструментов, время и результаты
   проверок. Не клади приватные ключи и runtime-конфиги с секретами в CI artifacts.

## Инциденты

- Сломан тест API: сборка/публикация/deploy заблокированы зависимостями jobs.
- Образ собирается, но приложение не ready: health gate ловит сбой.
- У deploy нет доступа к registry или VPS: ошибка диагностируется до смены релиза,
  либо выполняется проверенный rollback, если переключение уже началось.
- Неудачный релиз: `APP_PORT=oops` или неверный `DATA_DIR` только в учебном окружении.
  Предыдущий digest и правильный env восстанавливают API. Откат должен возвращать
  также изменённый конфиг, а не только образ.
- Два ручных запуска: убедись, что активен только один deploy.

## Приёмка и что сдать

- CI-конфиг и ссылки/логи успешной проверки PR, успешного deploy и неудачного релиза.
- Из manifest можно однозначно понять, какой commit запущен на VPS.
- Неуспешный тест блокирует релиз; failed health gate не помечается успешным deploy.
- Есть проверенный rollback образа **и конфигурации**, время восстановления записано.
- PR jobs не получают deploy-секреты, ключи и host keys настроены отдельно.

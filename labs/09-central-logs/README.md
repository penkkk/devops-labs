# 09. Логи с двух VM: Alloy → Loki → Grafana

**Время:** 3–5 часов. **Перед началом:** лаба 08, Grafana из лабы 05.

## Цель

Искать логи централизованно, связывать запрос proxy с API и понимать, почему ID
запроса полезен в содержимом лога, но не в индексных labels.

## Подготовка

На `mon` установи single-node Loki с локальным дисковым хранилищем; на `app` — Alloy.
Используй официальные инструкции и зафиксируй версии. Выдели отдельный каталог
для Loki, настрой retention 24 часа и алерт на заполнение диска. Retention не задаёт
жёсткую квоту размера: для неё нужна отдельная FS/квота или внешний контроль бюджета.
Удаление старых данных включается не одним сроком: проверь настройку compactor для
выбранного режима хранения по инструкции своей версии. Для малого стенда не делай
24-часовое ожидание обязательным: проверь конфиг и поясни, как проверишь удаление позже.

Для чтения stdout контейнеров выбери journald logging driver Docker в Compose
**только для этого проекта**, с постоянными tag `ops-demo` и `ops-proxy`.
Пересоздай контейнеры и найди фактические поля через `journalctl -o json`.
Alloy читает journal с необходимыми правами; Docker socket ему для этого не нужен.
Ограничь выборку этими tag, не отправляй весь системный журнал VPS.

Loki HTTP API слушает loopback и не публикуется в интернет. Для отправки из `app`
используй отдельный SSH-туннель `app:13100 → mon:3100`, либо закрытый private listener
с firewall только от `app`. Наличие private network само по себе не заменяет
ограничение доступа. Alloy на `app` отправляет в endpoint выбранного пути.

## Задания

1. Настрой Alloy: source journal, выборка только учебных контейнеров, извлечение
   нужного сообщения и отправка в Loki. Сохрани собственное состояние/positions
   Alloy вне временного каталога и проверь поведение после restart.
2. Оставь labels `job`, `host`, `service`, `environment`. JSON приложения разбирай
   так, чтобы `status`, `path` и `request_id` можно было фильтровать во время запроса.
   Не превращай timestamp, request ID и произвольный path в индексные labels.
3. Добавь Loki datasource в Grafana. Напиши LogQL: ошибки API за 15 минут, запросы
   `/items` с 503, все записи заданного request ID, число 5xx за 5 минут.
4. Проведи запрос через Nginx, найди его в обоих потоках по ID. Укажи временной
   диапазон и задержку доставки. Строка API внутри journal тоже JSON: проверь,
   что не пытаешься разбирать служебную оболочку как сообщение API.
5. Сопоставь пик 5xx на Prometheus dashboard со строками в Loki. Настрой ссылку
   с панели ошибок в Explore с нужным временным диапазоном.
6. Останови Alloy, создай 10 пронумерованных запросов, запусти Alloy. Посчитай
   доставленные записи и дубли; объясни реальные гарантии своего pipeline.
7. На 1 минуту разорви только путь доставки в Loki. Изучи логи и поведение буфера
   Alloy; затем восстанови путь. Не обещай бесконечный буфер и отсутствие потерь:
   зафиксируй лимиты и фактический результат эксперимента.

## Приёмка и что сдать

- Конфиги Alloy/Loki, список labels и четыре работающих LogQL-запроса.
- Один ID связывает Nginx и API; расследование выполняется из Grafana.
- Отчёт по restart агента и недоступности Loki с числом пропусков/дублей.
- Внешний доступ закрыт, retention/каталоги данных проверены, логи не содержат ключей.

## Контрольные вопросы

1. Чем фильтрация JSON-поля во время запроса отличается от индексного label?
2. Где могут потеряться логи: приложение, journal, агент, транспорт или Loki?
3. Почему отправка логов не заменяет метрики и наоборот?
4. Почему общий request ID ещё не означает наличие trace со spans?

Дополнительно после курса: инструментировать отдельный клиент и API через
OpenTelemetry, собрать spans в tracing backend и связать trace ID с логами.
Это отдельная работа по инструментированию; базовый `ops-demo` traces не создаёт.
